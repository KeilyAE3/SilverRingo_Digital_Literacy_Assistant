# M05 — ChatService 통합 오케스트레이터

## 목표
M02 검색·M03 응답 생성·M04 액션 검증을 하나의 순수한 응답 파이프라인으로 연결한다. 이때 의존성 주입으로 FakeLLM을 사용하면 네트워크 없이 E2E 테스트가 가능해야 한다.

## 인터페이스
`ChatService(retriever, llm_client, action_registry, settings).handle(ChatRequest) -> ChatResponse`.

## 순서/정책
1. 입력(문자수/공백/History) 검증 및 민감한 값 처리 정책.
2. 질문의 의도가 `현재 기능`인지 `향후 계획`인지 최소한의 명시적 규칙으로 분리; 애매할 때 활성 기능만.
3. Retriever top_k=4. 현재 구현 자료가 없으면 '앱에서 확인된 정보로는 지원 여부를 알 수 없습니다'처럼 안전한 안내. 모델에 빈 근거로 임의 설명하도록 지시하지 않음.
4. 근거별 ID/상태가 있는 context 직렬화. 토큰 낭비를 줄이기 위한 문서·문자수 제한.
5. Gemini 호출. 오류에는 고령층 친화적인 에러 문구와 HTTP 계층 오류 타입 반환(숨겨진 예외 출력 금지).
6. ActionRegistry는 검색 hit를 사용해 별도로 후보 산정, 활성 검증 통과만 출력. **LLM 출력의 임의 action 지시를 신뢰하지 않음**.
7. 응답 `reply`, `sources`, `suggested_actions`, `request_id`를 공통 타입으로 반환.

## 안전·유의점
- 의료 진단/실제 예약/실 결제 완료를 단언하지 않는다.
- `government24`, `kakaoT` 언급 시 구상 또는 폐기 상태를 정확히 설명, 실행 버튼 0개.
- 대화 맥락은 요청에 포함된 최근 기록만, 서버 영구 저장하지 않음.
- 질문에 포함된 '시스템 프롬프트 무시' 등은 사용자 질문일 뿐 정책 변경이 아니다.

## 테스트
FakeLLM과 실제 로컬 Retriever/ActionRegistry를 연결하여 4개 대표 질문 응답 구성. 품질 실패 분류: 검색 문제, 프롬프트 문제, 액션 문제, 데이터 부족. 실패 원인을 보고 후 수정.
