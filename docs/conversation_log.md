## 대화 1. 프로젝트 소개와 가능 여부 확인

**사용자 질문 (원문)**
> 나는 지금부터 어르신들을 대상으로 관공서, 주민등록본, 키오스크, 은행작업 등과 같은 온라인으로 할 수 있지만 잘 모르시는 분들을 위해서 'SilverLingo'라는 이름의 프로젝트를 팀원 넷이서 만들 계획이야
> 내가 맡은 부분은 관공서, 주민등록본, 키오스크, 은행작업 등과 같은 일을 사용자에게 필요한 정보만 입력받은 다음 알아서 입력되어서 저장되는 자동화 시스템을 만들 계획인데, 코드를 만들기전에 이론상으로 가능한지 여부를 확인해줘

**답변 요약**
- 실제 관공서·은행 사이트를 자동화하는 것은 **기술적·법적으로 어려움**.
- 기술적 장애물: 본인인증(공동인증서, 간편인증), 키보드 보안·가상 키패드, CAPTCHA, 잦은 화면 변경. 키오스크는 오프라인 기기라 원격 자동화 불가.
- 법적 장애물: 전자금융거래법(접근매체 양도·대여 금지), 개인정보보호법 제24조의2(주민번호 처리 제한), 정보통신망법, 신용정보법(마이데이터 허가제), 주민등록법(대리 발급은 위임 절차 필요).
- 원칙: 인증 정보(비밀번호, 인증서, 주민번호)는 저장하지 않는다.

## 대화 2. 법적 문제 업무는 안내로 대체 + 다른 업무 자동화

**사용자 질문 (원문)**
> 법적으로 문제가 있는 부분은 자동화 대신 홈페이지 사진에다 설명해주는 부분을 따로 올리면 좋을것 같고, 저 4개말고도 어르신들이 잘 하지 못하는 온라인 업무같은것들을 자동화할 수 는 없을까?

**답변 요약**
- 법적으로 문제 되는 업무는 **실제 화면 사진 기반 안내**로 대체 (→ 대화 4에서 연습 시뮬레이터로 발전).
- 🟢 완전 자동: 복지 혜택 찾기⭐, 기초연금 계산, 문자 사기 판별⭐, 고지서 사진 풀이⭐, 병원·약국 찾기, 버스·기차 조회, 택배 조회, 노인 일자리, 폭염·한파 쉼터
- 🟡 반자동: 신청서·위임장 자동 작성⭐, 공과금 알림, 약 복용 알림, 병원 예약 준비, 기차·버스 예매 준비(예매 매크로는 쓰지 않음)
- 🔴 안내/시뮬레이터: 정부24 등본, 은행 이체, 홈택스, 건강검진·국민연금 조회, 택시·배달·쇼핑 앱, 키오스크
- 추천 우선순위: 복지 혜택 찾기 → 문자 사기 판별 → 고지서 사진 풀이 → 신청서 자동 작성

## 대화 3. 발표용 본인인증 직접 구현

**사용자 질문 (원문)**
> 우리가 진짜 상용화 하려고 구체적으로 하는것은 아니지만 팀 프로젝트로 발표를 해야하는데, 본인인증 구현을 따로 만들어서 할 순 없을까?

**답변 요약**
- **가능함**. 본인인증 서버, 가짜 정부24, 가짜 은행을 모두 직접 만들고 **그 안에서만** 처음부터 끝까지 자동화를 시연.
- 인증 방식: **간편인증 흐름 따라 만들기(휴대폰 승인) + WebAuthn(지문·얼굴)**
- 시연 시나리오: "김순자 할머니 등본 발급" → 자동 입력 → 휴대폰 승인 + 지문 → PDF 저장 + 음성 안내
- 주의: 실제 브랜드를 따라 하지 않기("SilverLingo 민원24", "실버은행"), "데모" 표시, 가짜 데이터만 사용, 우리 사이트 주소로만 접속하게 고정

## 대화 4. 실제 사이트로 이어지는 연습 시뮬레이터

**사용자 질문 (원문)**
> 아 그 자동화가 불가능한 것들을 우리가 따로 빼서 시뮬레이션으로 만들때 시뮬레이션만 제대로 숙지하면 정식 홈페이지에 들어가서 그대로 따라할 수 있게 만드는것도 돼?

**답변 요약**
- **가능함**. 시뮬레이터는 실제와 **최대한 똑같이** 만들어야 실전에서 따라 할 수 있음.
- 방식: **실제 화면 캡처 + 클릭 영역 + JSON 시나리오**. 사이트가 바뀌면 캡처와 좌표만 수정.
- 학습 단계: 보기 → 따라 하기 → 혼자 하기 → 실전
- 실제 상황 재현: 인증 시간 초과, 팝업, 보안 프로그램 안내, 간편인증 앱 전환, 입력 오류, 진짜 사이트 주소(`gov.kr`) 확인
- "연습용" 표시, 실제 정보는 입력받지 않기, 캡처 날짜 표시
- 비슷한 기존 서비스(NIA 디지털배움터, 은행 시니어 교육 앱 등)와의 차별점을 발표에서 강조

## 대화 5. 모바일 화면 중심 설계

**사용자 질문 (원문)**
> 추가로 우리는 휴대폰을 잘 다루지 못하시는 분들을 위해서 만드는 것이니 만큼 웹사이트를 만들때 모바일 화면에 맞춰서 만들고 싶어

**답변 요약**
- 시뮬레이터는 **모바일 앱·모바일 웹 화면**으로 캡처하고, 클릭 영역은 **비율 좌표** 사용.
- 실전 모드(폰 한 대 기준): 음성 안내, 안내 카드 저장, 가족 공유
- 본인인증 연습: 같은 폰에서 인증 앱으로 넘어갔다가 돌아오는 과정 재현
- 자동화 데모: 엔진은 서버에서 실행, 폰에는 진행 화면만 표시
- 설계 기준: 글자 20px 이상, 버튼 56~64px, 대비 7:1, 한 화면에 한 가지 일, 햄버거 메뉴 금지, 아이콘 + 글자, 누르기만 사용, 주요 버튼은 아래쪽 고정
- 입력 부담 줄이기: 음성 입력, 음성 읽어주기, 숫자 키패드, 고르기 위주, 글자 크기 조절, 확인 창
- 기술: 360~412px 기준 모바일 우선, **PWA**, PC에서는 가운데 최대 480px
- 발표: Smart View나 scrcpy로 폰 화면 띄우기, 또는 휴대폰 모양 틀 사용

## 대화 8. 기차 업무 역할 분담 (코레일 조회 자동화 + 예매 시뮬레이터 연계)

**사용자 질문 (원문)**
> 기차 조회는 자동화로 된다고 했는데, 기차 조회는 코레일 홈페이지에서 조회할 수 있게 해주고, 예매만 시뮬레이션으로 하게 해줬으면 좋겠어

**답변 요약**
- **기차표 조회**: 코레일 홈페이지(letskorail.com)와 연동하여 실시간 열차 시간표·요금·잔여석을 **자동 조회**.
- **기차표 예매·결제**: 실제 결제·매크로는 약관 및 법적 규제가 있으므로, 조회된 열차를 바탕으로 **코레일톡 예매 시뮬레이터(좌석 선택 ➔ 모의 결제 ➔ 승차권 발행)** 로 연결하여 안전하게 연습하도록 분리 확정.
- UI 화면 및 시뮬레이터 연계 흐름 프로토타입 구현 완료.

## 대화 9. 완전 자동화의 핵심 메커니즘 (앱 입력 ➔ 홈페이지 자동 입력 및 결과 추출)

**사용자 질문 (원문)**
> 완전 자동화가 가능한것은 앱에서 홈페이지로 바로 연동해주고, 필요한 정보를 앱애 입력하면 앱이 알아서 홈페이지에 정보를 입력해줘서 알아내는게 목표야

**답변 요약**
- **SilverLingo 자동화의 핵심 본질 확정**:
  - 어르신은 복잡한 외부 홈페이지를 직접 다룰 필요 없이 **앱에서 필요한 정보만 큰 글씨로 입력**.
  - 시스템(Playwright RPA 엔진)이 **해당 공식 홈페이지로 직접 접속하여 입력창에 자동으로 값을 채워 넣고(Form-Filling)** 조회 버튼을 클릭.
  - 홈페이지의 복잡한 화면에서 **어르신에게 꼭 필요한 핵심 정보(시간표, 잔여석, 지원 혜택 등)만 깔끔하게 추출**하여 앱 화면에 보여줌.
- 코레일 기차표 조회 및 데모 사이트 자동화에 이 프로세스(사이트 접속 ➔ 자동 폼 입력 ➔ 결과 파싱)를 시각적으로 연출하고 백엔드 엔진으로 구현하기로 반영.

## 대화 10. 복지 혜택 조회 ➔ 실제 수령 및 신청서 연계

**사용자 질문 (원문)**
> 복지혜택 찾기를 한번 봤는데, 원래 이건 조회만 하는거고 복지 혜택 실제로 받으려면 다른 방법이 없어?

**답변 요약**
- 조회에 그치지 않고 실제 수령 방법(주민센터 방문, 서류 없이 신분증 지참, 무료 병원 찾기)을 행동 버튼으로 직접 연결.
- 특히 기초연금의 경우 **"기초연금 신청서 자동 완성"** 기능으로 바로 이어져, 어르신의 인적사항이 채워진 출력용 신청서가 즉시 생성되도록 구현.

## 대화 11. 모바일 앱 기술 스택 검토 (Kotlin + Jetpack Compose vs React Native)

**사용자 질문 (원문)**
> 아 그리고, 우리가 기술 개발 스택을 둘중 하나 택1을 해야하는데, 너의 의견이 필요해
> Android만 확정: Kotlin + Jetpack Compose / Android 우선, 3차에서 iOS 지원까지 고려: React Native + Expo

**답변 요약**
- **Kotlin + Jetpack Compose 강력 추천 확정**:
  1. 어르신의 90% 이상이 삼성 갤럭시(Android) 사용
  2. 다른 앱(정부24, 코레일톡) 위에 안내 말풍선을 띄우는 핵심 킬러 기능(System Overlay / AccessibilityService)은 네이티브 Android에서만 완벽히 지원됨
  3. 사용자의 Java 지식이 Kotlin에 그대로 활용 가능하여 학습 장벽이 낮음
  4. 발표 시 "시스템 레벨의 깊이 있는 안드로이드 엔지니어링"으로 높은 기술 평가 획득 가능

## 대화 12. 사용자 직접 정보 입력 & 로컬 저장 및 서류 자동 연동

**사용자 질문 (원문)**
> 아직 사용자한테 직접 입력받는 기능은 안만든거지?
> 어 구현 한다음에 지금까지 구현해놓은거 저장해주고 띄워줘

**답변 요약**
- **👤 내 기본 정보 등록 (최초 1회 입력)** 기능 구현:
  - 성함, 생년월일(6자리), 주소, 환급/연금 계좌번호를 직접 입력하고 기기에 안전하게 저장(`localStorage`).
  - 저장된 사용자 정보가 메인 환영 인사, 주민등록등본 발급(자동 채움), 기초연금 신청서(이름/주소/계좌 자동 주입), 관공서 서류 작성에 실시간으로 연동되도록 완성.
- 브라우저에 실시간 반영 및 실행 완료.

## 대화 13. 즉시 상용화(Production-Ready) 전환 방향 수립

**사용자 질문 (원문)**
> 아 근데 상용화 목적이 아니라고는 했는데, 조금만 더 개발했을때 바로 상용화까지 할 수 있도록 하는 방향으로 해줘

**답변 요약**
- **프로젝트 목표 개정**: 발표용 데모에 머무르지 않고, **조금만 추가 개발하면 구글 플레이스토어에 즉시 배포 가능한 프로덕션 레디(Production-Ready) 아키텍처**로 격상.
- **3대 상용화 핵심 설계**:
  1. **개인정보 제로-서버 원칙 (On-Device Zero-Knowledge)**: 개인정보는 서버 DB에 일체 저장하지 않고 기기 내 로컬 암호화 저장소에만 보관 ➔ 복잡한 ISMS 인증 및 법적 규제 없이 즉시 상용 서비스 출시 가능.
  2. **모듈형 인터페이스 (Config-Driven Switch)**: 데모용 Mock 모듈과 실제 공공 마이데이터/공공데이터포털 연동 모듈을 인터페이스로 분리하여 설정 하나로 실서비스 전환 가능하도록 설계.
  3. **Android 네이티브(Kotlin + Compose) 확장 준비**: 접근성 서비스(Accessibility) 및 시스템 오버레이 규격 준수.

## 대화 15. 실제 사이트 이동 시 실시간 오버레이 가이드 제공 가능 여부 및 3가지 구현 방식

**사용자 질문 (원문)**

**답변 요약**
- **기술적 제약 확인**: 일반 웹 브라우저의 단순 링크 이동 방식은 브라우저 보안 정책(Same-Origin Policy, XSS/피싱 방지)으로 인해 타 사이트(정부24, 코레일 등) 화면을 직접 조작하거나 오버레이를 얹을 수 없음.

  1. **[방법 A. 스마트폰 모바일 앱 플로팅 도우미 (Android System Overlay - 상용화 킬러 기능 ⭐)]**:

  2. **[방법 B. 브라우저 확장 프로그램 (Chrome Extension)]**:
     - PC/태블릿 크롬 브라우저 환경에서 실제 사이트 접속 시 Content Script를 주입하여 입력창 바로 위에 하이라이트 박스와 안내 말풍선 오버레이 렌더링.
  3. **[방법 C. 웹 전용 가이드 분할 화면 / 동행 플로팅 바 (현재 웹 데모용)]**:
     - 순수 웹 데모 환경에서 링크 이동 시 상단에 [실시간 실전 가이드 바]를 띄워 어르신이 실제 사이트 진행 시 1단계, 2단계 체크리스트와 음성 안내를 함께 보며 진행하도록 지원.

## 대화 16. 완전 자동화 제외 및 서드파티 플로팅 오버레이 도우미로 단일화

**사용자 질문 (원문)**
> 내가 완전 자동화가 되는것과 안되는것을 구분해서 각기 다른 방식으로 진행하는 거였는데, 팀원들과의 논의로 인해서 캔버스가 너무 커질것 같아서 완전자동화를 그냥 빼버리고 '앱을 서드파티 앱 형태로 작게 띄워놓고 앱을 통해 사이트에 들어가면 오버레이 방식으로 필요한 입력부분을 알려주거나, 간단한 설명과 함께 사이트에서 수월하게 어르신들이 필요한 행동을 할 수 있게 하는 방식'만 하기로 했어

**답변 요약**
- **방향성 전격 피벗 & 범위 압축 (단일 핵심 가치 집중)**:
  - 범위가 너무 방대해지는 것을 방지하기 위해 **서버 완전 자동화(Playwright 대리 폼필링·로그인)는 전면 제외**.
  - 대신 **'서드파티 플로팅 오버레이 동행 도우미(Overlay Companion)' 단일 모델에 집중**.
- **서드파티 플로팅 오버레이 방식의 핵심 메커니즘**:
  1. SilverLingo 앱이 화면 한구석에 **작은 서드파티 플로팅 위젯(버블/미니바)** 형태로 떠 있음.
  2. 어르신이 앱을 통해 실제 대상 사이트(정부24, 코레일, 은행 등)에 진입하면:
     - **오버레이 가이드**: 실제 사이트 화면 위에 직접 포커스 링/스포트라이트를 쏘아 **"지금 입력하거나 눌러야 할 곳"**을 시각적으로 짚어줌.
     - **쉬운 설명 & 음성**: 어려운 행정/금융 용어를 걷어내고, 큰 글씨 말풍선과 🔊 음성으로 "여기에 생년월일 6자리를 적으세요", "파란색 발급신청 버튼을 누르세요"라고 단계별 가이드.
     - **어르신의 주도적 완료**: 시스템이 억지로 가로채지 않고, 어르신이 직접 보고 누르며 성취감을 느끼고 수월하게 업무를 마칠 수 있도록 동행.
- **피벗의 절대적 이점**:
  - **법적/보안 리스크 제로**: 서버에 주민번호나 비밀번호를 수집·대리 전송하지 않으므로 개인정보보호법·전자금융거래법 위반 소지 0%.
  - **프로덕션 레디 상용화에 완벽 부합**: 안드로이드 `SYSTEM_ALERT_WINDOW`(다른 앱 위에 그리기) 권한을 활용하여 어떤 앱/웹사이트 위에서도 동작하는 유틸리티 앱으로 구글 플레이스토어 즉시 등록 가능.
  - **팀 프로젝트 완성도 극대화**: 이원화(자동화+시뮬레이터)로 분산되던 개발 리소스를 고품질 오버레이 인터랙션에 온전히 집중 가능.

## 대화 19. 도우미의 버튼 가림 현상 해결 및 진행 단계 자동 이동(Auto-Advance) 파이프라인

**사용자 질문 (원문)**
> 도우미가 뜨는건 확인했는데, 버튼을 눌러야 하는데 도우미가 가려버리는 현상이 있어.
> 그리고 직접 사이트 위에서 알려주는걸 했으니까 진행단계도 알아서 이동해야 해

**답변 요약**
- **버튼 가림 현상(Occlusion) 100% 원천 차단**:
  1. **스마트 위치 계산(Smart Placement Engine)**: 타깃 버튼의 높이와 말풍선 크기를 실측하여 타깃 바깥(기본: 버튼 상단 20px 위 / 공간 부족 시: 버튼 하단 20px 아래)으로 분리 배치하고, 뾰족한 화살표 꼬리표(`silverlingo-tooltip-arrow`)로 버튼을 가리킴.
  2. **클릭 관통 및 위임(Click Delegation)**: 스포트라이트 박스는 `pointer-events: none`으로 클릭을 100% 관통시키고, 사용자가 말풍선 자체를 누르더라도 타깃 버튼 클릭이 즉시 실행되도록 위임 이벤트 등록.
  3. **위치 비키기 버튼(`↕ 위치 비키기`)**: 말풍선 상단에 비키기 버튼을 두어 사용자가 언제든 반대편으로 도우미를 이동 가능.
  4. **플로팅 바 자동 충돌 회피(`dock-top`) 및 최소화(`—`)**: 화면 하단 버튼과 플로팅 바가 겹치면 플로팅 바가 상단으로 자동 대피하며, 원형 아이콘으로 접을 수 있는 최소화 기능 추가.
- **알아서 척척 이동하는 자동 진행(Auto-Advance) 상태 머신 탑재**:
  1. **화면/URL별 정밀 분기**:
     - **Step 1 (메인 `plus.gov.kr`)**: [주민등록등본(초본)] 서비스 바로가기 링크 타깃팅
     - **Step 2 (민원안내 상세 `AA020InfoCappView.do`)**: 우측 파란색 **[발급하기]** 버튼 자동 타깃팅 (이전 버전의 본문 텍스트 오탐 완벽 해결)
     - **Step 3 (로그인/인증 모달 또는 페이지)**: [비회원 신청하기] 또는 [카카오톡 간편인증] 버튼 자동 타깃팅
     - **Step 4 (민원신청서 작성 `AA040`)**: 파란색 [민원신청하기] 버튼 자동 타깃팅
  2. **실시간 감시 & 피드백**: 버튼 클릭 시 즉시 🔊 "잘 누르셨습니다! 다음 화면으로 이동하고 있습니다." 음성 송출과 함께 `MutationObserver` 및 URL 감시자가 새 화면을 0.3초 내에 감지하여 다음 단계 오버레이로 자동 전환.
- **실전 브라우저 테스트 완료**: `chrome://extensions` 재로드 후 `https://plus.gov.kr/`에서 등본 버튼 클릭 시 상세 페이지의 파란색 [발급하기] 버튼으로 매끄럽게 자동 이동 및 비간섭 오버레이 렌더링 검증 완료.

1. **홈 진입 게이트 `hasReachedHome`**: 1단계 검색창("질병, 진료과"/"병원 검색"/"병원검색")이 보이면 켜짐. 꺼져 있는 동안 2~7단계 탐색 안 함(권한 [허용]/[건너뛰기] 안내만). 끝부분의 "카카오로 시작"/"시작하기" 안내 제거.
2. **`isAuthOrSignupScreen`**: 보이는 노드의 text·contentDescription·hintText를 DFS로 검사(`AUTH_KEYWORDS` 15개: 회원가입, 약관, 본인인증/본인 인증, 본인확인/본인 확인, 인증번호, 통신사, 문자(SMS), 보안문자, 주민등록번호, 생년월일, 휴대폰번호, 이메일 로그인, 카카오로 시작). 감지 시 `hasReachedHome = false` + 오버레이 제거.
3. **2단계**: 포커스된 입력창의 문구에 질병/진료과/병원/검색/증상이 있거나 현재 1·2단계 안내 중일 때만. **6단계**: "인증"/"확인"이 포함된 "본인" 문구 제외(`findNodeByKeywords`의 `exclude`).
4. **타깃 미발견 시** 창 전환 여부와 관계없이 즉시 오버레이 제거.
5. `assembleDebug` 성공, 바탕화면 `SilverLingo_v3.0.7_인증화면_오버레이차단.zip`.
