# Silver Ringo C파트 — 자료 분석 및 구현 검토

검토일: 2026-10-24. 범위: C 학습 콘텐츠. A 메뉴/외부 앱, B 실제 업무 수행, D 챗봇은 구현하지 않았다.

## 1. 원본 자료에서 확인한 사실

- `silver-ringo-v2.zip`은 약 5KB이며 `index.html`(8,093 bytes), `KioskPracticeScreen.kt`(754 bytes), README(866 bytes) 세 파일만 포함한다. Android 프로젝트·Gradle 설정·테스트·상품 이미지 파일은 없다.
- 별도로 저장된 최신 `index.html`은 ZIP의 HTML과 바이트 단위로 동일했다. 별도의 고도화된 버전으로 취급하지 않았다.
- 메인 UI 이미지는 남색 헤더·노란 포인트·연회색 배경·큰 흰 카드가 핵심이다. 개선판의 학습 화면에 반영했다. A의 메인 메뉴나 챗봇은 복제하지 않았다.
- PDF는 8쪽 모두 손그림 기반이며 추출 가능한 텍스트는 없었다. 1~4쪽의 전체 앱 스케치와 5~8쪽을 렌더링해 검토했다. 5쪽은 원형 노드와 연결선 형태, 6~8쪽은 추상적인 스케치다. 세부 레벨 이름·정답 조건·치수는 PDF에서 확정할 수 없으므로 인수인계서의 설명을 설계 기준으로 사용했다.
- 롯데잇츠 링크의 공개 이벤트 페이지와 키오스크 매뉴얼 안내는 확인했다. 해당 페이지 텍스트만으로 내부 시뮬레이터의 실제 전체 화면과 상호작용을 검증하지는 못했다. 공식 화면과 동일하다고 주장하지 않는다. 로고·상품명·이미지·코드는 복제하지 않았으며 가상 브랜드와 자체 SVG 그림을 사용한다.

재사용한 것은 색상 방향·주문 흐름·모드 개념이다. 단일 HTML 내부 전역 변수와 `onclick` 문자열 구조는 확장과 판정 분리에 맞지 않아 C파트 내부에서 역할별 파일로 정리했다. 기술 스택은 기존 HTML/JS + Compose WebView를 유지했다.

## 2. 실제 키오스크에 가까운 실습

가상 매장 `RINGO BURGER`의 세로형 단말을 만들었다. 시작 → 취식 장소 → 카테고리/상품 → 옵션 선택 패널 → 장바구니 → 주문 확인 → 결제 수단 → 모의 결제 → 주문번호 순서다. 단품 주문, 다른 메뉴, 추가 담기, 삭제, 이전 화면, 잘못된 목표 수행도 허용한다. 교육용 목표와 주문 가능한 행동을 구분해 마지막에 목표 달성 여부를 판정한다.

단말은 실제 매장 사진의 복제본이 아니다. 화면을 좁게 고정해 읽기 어렵게 만드는 대신 모바일 폭에서는 화면 전체를 쓰고 데스크톱에서는 세로형 단말 옆에 교육 안내를 둔다. 옵션 패널은 전체 페이지 내부의 선택창으로 구성해 별도 모달 포커스 함정 없이 키보드로 조작할 수 있다. 사용성 검증 후 실제 모달로 바꿀 수 있다.

학습에서는 현재 조작 대상에 문구와 테두리를 함께 표시한다. 실전에서는 정답 강조와 자동 안내를 없애고 목표만 제공한다. 원하면 힌트를 요청할 수 있으며 횟수를 기록한다. 시간제한·자동 결제·외부 결제 SDK·개인정보 입력은 없다.

## 3. 웹/Android 구조 비교와 추천

| 기준                 | 방식 1: Compose 네이티브 + 별도 웹                 | 방식 2: Compose + WebView 실습                                 |
| -------------------- | -------------------------------------------------- | -------------------------------------------------------------- |
| 초기 난이도          | 주문 UI/상태를 두 환경에 구현해야 해 높음          | 실습 구현 하나를 재사용하므로 낮음                             |
| 유지보수             | 기능 수정 때 두 화면과 동작을 맞춰야 함            | 실습 수정은 한 번, 브리지·WebView 버전 관리 필요               |
| 코드 재사용          | 콘텐츠 JSON·명세는 공유, UI 직접 공유는 어려움     | HTML/CSS/JS·상품 이미지·판정 엔진을 그대로 공유                |
| 테스트 편의          | 웹 테스트 외 Android UI 테스트도 별도 필요         | 브라우저에서 대부분 검증, 브리지/TTS/생명주기는 기기 검증 필요 |
| 접근성               | Compose semantics·TalkBack·시스템 글꼴에 직접 대응 | HTML 의미 구조 지원, WebView/TTS/글꼴 확대는 기기별 확인 필요  |
| 네이티브 목표 적합성 | 최종 목표에 가장 직접적                            | 단기 MVP에 유리, 최종 실습 UI의 Kotlin 전환 비용 남음          |
| 오프라인             | 로컬 콘텐츠로 가능                                 | APK 내 웹 자산으로 가능                                        |

**추천: 단기 MVP는 방식 2, 최종 목표는 방식 1의 Android 네이티브 화면.** 현재 ZIP의 방식 2를 유지해 주문 시뮬레이터부터 검증한다. 학습 목록/단계 잠금/진입점은 Compose이며, 실습만 WebView로 묶는다. 이후 검증된 `OrderState / Action / Goal / Result` 계약을 Kotlin으로 포팅하고 Compose 실습 UI로 교체한다. Kotlin과 JS 사이에 복잡한 양방향 공유 엔진이나 서버를 추가하지 않는다. 전면 네이티브 전환은 이번 작업에 포함하지 않았으며 착수 전 별도 확인 대상이다.

Android는 `file://` 대신 WebViewAssetLoader의 로컬 HTTPS 자산을 사용한다. 외부 이동과 리소스는 차단하고 정해진 origin의 메인 프레임 메시지만 받는다. 이는 Android 공식 로컬 콘텐츠 가이드를 따른다. WebView의 음성을 브라우저 구현에만 의존하지 않고 Android TextToSpeech로 전달한다.

완료 판정은 로컬 교육용이다. 부정행위 방지나 고신뢰 인증을 제공하지 않으며 필요 이상의 서버·로그인·클라우드 저장은 두지 않았다.

## 4. 폴더 및 모듈 구성

| 경로                                     | 책임                                               |
| ---------------------------------------- | -------------------------------------------------- |
| `web/content.js`                         | 상품, 가격, 레벨 설명, 목표 조건 키, 안내 문구     |
| `web/content.json`                       | 동일 콘텐츠의 Android용 직렬화 결과                |
| `web/engine.js`                          | 주문 상태·전이·가격·결과 판정, DOM 의존성 없음     |
| `web/app.js`                             | 화면 표시, 이벤트 연결, 저장, TTS, 네이티브 메시지 |
| `web/styles.css`                         | 학습 UI와 실습 UI의 시각적 구분, 반응형 크기       |
| `web/assets`                             | 자체 제작 메뉴 SVG                                 |
| `android/app/.../LearningEntry.kt`       | A에서 부를 수 있는 Compose 학습 진입점, 목록/잠금  |
| `android/app/.../KioskPracticeScreen.kt` | WebView 자산 호스트·메시지·TTS·생명주기            |
| `tests`                                  | 주문 엔진 테스트와 브라우저 상호작용 검증          |
| `scripts`                                | 콘텐츠 JSON 동기화, 단일 파일 데모 생성            |
| `docs`                                   | 분석·연동 계약·검증 범위                           |

현재 규모에서는 Gradle 멀티모듈·DI 프레임워크·서버를 도입하지 않았다. 팀 통합 시 `kr.silverringo.learning` 패키지를 `:feature:learning` Android library로 이동하면 된다. 호스트 앱의 AGP/Kotlin/Compose BOM 버전을 따르고 `MainActivity`는 데모에서만 사용한다.

**A 연결:** `LearningEntry(onExit, onResult)` 호출. 외부 앱 실행이나 A의 내비게이션은 C가 소유하지 않는다. `onResult` JSON은 `schemaVersion/topicId/levelId/mode/passed/failures/hints/actions/elapsedSeconds/completedAt` 필드를 가진다.

**B 공유 가능 부분:** `StepDefinition(id, instruction, targetKey, nextStepId)` 같은 안내 데이터와 큰 안내 카드·반복 음성 UX는 공유할 수 있다. B의 실제 사이트 조작 성공 조건과 C의 모의 주문 GoalEvaluator를 공유하지 않는다. 현재 B 엔진을 임의 구현하거나 수정하지 않았다.

**다른 학습 추가:** 새 콘텐츠 정의·시뮬레이터 reducer·평가기를 추가하고 topicId로 진입하도록 확장한다. 문자 학습은 기기의 실제 문자 발송 API를 호출하지 않는 별도 모의 화면으로 구현한다. 현재 가격/상품 엔진은 키오스크 전용이며 모든 콘텐츠에 재사용된다고 과장하지 않는다. 레벨/결과/안내 계약이 공통화 대상이다.

## 5. MVP 순서 (C파트 1인 기준 예시, 실제 일정 보장 아님)

1. 1~2일: 기존 주문 오류 확인 → 상태·가격 계산 분리. 이번 개선판에 반영.
2. 2~3일: 메뉴/옵션/장바구니/확인/모의 결제 전체 흐름. 이번 개선판에 반영.
3. 1~2일: 부분 레벨·목표 판정·재시도·진도·TTS. 웹 구현과 Android 연결 코드 반영.
4. 1~2일: Android Studio 빌드, 실기기 TTS/TalkBack·시스템 뒤로가기·화면 회전 확인. 이 환경에서 미검증, 다음 우선 작업.
5. 1~2일: 고령 사용자 2~3명 관찰 후 문구/터치 크기/옵션 화면 개선. 아직 미수행.
6. 이후: 팀 통합. 네이티브 실습 전환 범위와 비용 확인 후 Kotlin reducer/Compose 실습 구현.
